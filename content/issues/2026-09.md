## Security

### 0.23.45

_Published September 14, 2026 · 2 sources_

**Bug fix**: TLS 1.3 handshake messages incorrectly accepted across encryption level boundaries

Rustls accepted TLS 1.3 handshake messages sent at the wrong encryption level when they followed a key-changing message in the same record. The handshake transcript is still authenticated, so a network-position attacker cannot use this to alter or complete a handshake; the practical effect is that a peer could send handshake messages that should be encrypted in plaintext without rustls rejecting the connection.

This issue is tracked as [GHSA-2mjx-qc3c-rqvc](https://github.com/rustls/rustls/security/advisories/GHSA-2mjx-qc3c-rqvc). This issue affects rustls versions 0.23.13 through 0.23.44 inclusive.

Note that this is functionally the same bug as [GO-2026-4340](https://pkg.go.dev/vuln/GO-2026-4340).

**Sources:** [release notes](https://github.com/rustls/rustls/releases/tag/v/0.23.45) · [crates.io](https://crates.io/crates/rustls/0.23.45)

### TLS 1.3 handshake messages incorrectly accepted across encryption level boundaries

_Published September 14, 2026_

Rustls accepted TLS 1.3 handshake messages sent at the wrong encryption level when they followed a key-changing message in the same record. For example, a plaintext `EncryptedExtensions` message packed into the same record as the `ServerHello` was accepted.

RFC 8446 section 5.1 requires that handshake messages do not span key changes, and that implementations terminate the connection with an "unexpected_message" alert if they do.

The handshake transcript is still authenticated, so a network-position attacker cannot use this to alter or complete a handshake; the practical effect is that a peer could send handshake messages that should be encrypted in plaintext without rustls rejecting the connection.

This is functionally the same bug as Go's [GO-2026-4340](https://pkg.go.dev/vuln/GO-2026-4340) (CVE-2025-61730).

**Sources:** [security advisory](https://rustsec.org/advisories/RUSTSEC-2026-0285.html)

### GitHub Actions leaking secrets when Miri output is cached

_Published September 21, 2026_

<p>The Rust Security Response Team was notified that Miri stores all environment variables to <code>target/</code>, allowing secrets to persist in caches.</p> <p>While not necessary a vulnerability in and of itself, when paired with GitHub Actions caching behavior, it is possible for this to expose secrets to PRs.</p> <h2 id="overview"><a class="anchor" href="#overview" aria-hidden="true"></a> Overview</h2> <p>GitHub Actions makes it possible to cache directories between runs. Typical setups allow CI runs on <code>main</code> (and other branches) to <em>write</em> to cache, and PRs can only <em>read</em> from cache (preventing cache poisoning). Rust projects tend to speed up CI by caching binaries built by <code>cargo install</code> and sometimes the contents of <code>target/</code>.</p> <p>PR CI can be triggered by anyone who can open PRs on your repository. GitHub requires maintainer approval for the <em>first</em> PR, but future PRs will rerun CI on every push. Anyone who has previously landed a change can trigger a CI run extracting information from cached <code>target/</code> and then cover their tracks by pushing a second commit to the PR.</p> <p>GitHub sometimes hides overwritten commits in its UI, making this kind of attack harder to detect. CI run logs and overwritten commits are also deleted after a few months.</p> <p>When <code>cargo miri</code> is invoked, Miri needs to retain build-relevant environment variables between runs<sup class="footnote-reference" id="fr-1-1"><a href="#fn-1">1</a></sup>. The current code to do so achieves this by storing <a rel="external" href="https://github.com/rust-lang/miri/blob/165a9c3c96f0f4e6232278e62cb64648215bbc37/cargo-miri/src/util.rs#L40-L42">all environment variables to <code>target/</code></a>. This, of course, persists when <code>target/</code> is cached.</p> <p>If your environment contained secrets, these can now be accessed by PRs via the cache.</p> <h2 id="our-fix"><a class="anchor" href="#our-fix" aria-hidden="true"></a> Our fix</h2> <p>Our <a rel="external" href="https://github.com/rust-lang/miri/pull/5337">short term fix</a> for this is to make Miri only preserve <code>CARGO_*</code> environment variables (excepting <code>CARGO_*_TOKEN</code>) and <code>OUT_DIR</code>. Rust is a programming language that is empowering everyone to build reliable and efficient software.</p> <p>If you have a previous version of Rust installed via rustup, getting Rust 1.98.1 is as easy as:</p> <pre class="giallo z-code"><code data-lang="plain"><span class="giallo-l"><span>rustup update stable</span></span></code></pre> <p>If you don't have it already, you can <a rel="external" href="https://www.rust-lang.org/install.html">get <code>rustup</code></a> from the appropriate page on our website.</p> <h2 id="what-s-in-1-98-1"><a class="anchor" href="#what-s-in-1-98-1" aria-hidden="true"></a> What's in 1.98.1</h2> <p>Rust 1.98.1 fixes a <a rel="external" href="https://github.com/rust-lang/rust/issues/161441">miscompilation in vtable generation</a>.</p> <p>In Rust 1.98.0, in some circumstances, rustc would incorrectly generate a trait object vtable with a null pointer where a function pointer should be. This leads to undefined behavior in the emitted code. In some cases this may 'just' cause segfaults due to the null pointer being loaded, but it is possible for it to be justification for arbitrary effects (as is typical for UB).</p> <p>If you'd like to help us out by testing future releases, you might consider using the beta (<code>rustup default beta</code>) and nightly (<code>rustup default nightly</code>) channels locally and in your CI.
